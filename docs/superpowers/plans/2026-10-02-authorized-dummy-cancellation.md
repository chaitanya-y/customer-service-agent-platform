# Authorized dummy-payment cancellation plan

Status: **partially implemented, not enabled or end-to-end verified**. The Gateway reservation, exact-payment contract, purpose-scoped assertions, and Temporal Worker path have offline tests, but the customer path and running Gateway server are deliberately unwired. The Vendure provider is not registered because a controlled concurrency test found that its local SQLite/TypeORM connection can treat two independent Admin requests as nested transactions: rolling back cancellation can also undo a concurrently successful fulfillment. That violates the required atomicity boundary. An independent-transaction backend is necessary but not sufficient: Vendure's normal settlement and fulfillment paths do not share the cancellation marker lock, so stale-read races must also be prevented or rejected. A proven cross-mutation serialization/constraint design and deterministic race/rollback tests are required before enabling this policy. The first narrow no-payment zero-total policy remains `NO_PAYMENT_ZERO_TOTAL_V1` and must not change meaning. This next policy is `AUTHORIZED_DUMMY_V1`, for a locally simulated authorization only. It is not a real bank hold release and does not cover a settled payment.

## Outcome and boundaries

An authenticated customer can review and explicitly confirm cancellation of an unfulfilled, placed Vendure order with exactly one **authorized local dummy** payment. The journey may show completion only after an authoritative provider marker and fresh provider reads prove both the order and the one payment are `Cancelled`. It must not use the refund workflow, silently cancel on a chat turn, issue a refund, or claim a real PSP void.

Eligibility is intentionally narrow: matching customer/tenant/environment/channel, `Regular` order, placed and inactive in `PaymentAuthorized`, positive safe-integer total, unchanged positive original line quantities, no fulfillment, exactly one payment whose state is `Authorized` and amount equals the order total, no refunds, and a channel-enabled payment method whose actual configured handler is Vendure's installed `dummy-payment-handler`. `Payment.method` is a method code, not proof of its handler. Missing or ambiguous facts fail closed.

The preview binds policy version, owner/order/payment IDs, order reference, exact full-order amount/currency, item quantities, provider facts digest, and a 15-minute deadline. The customer-facing consent says the order **and simulated payment authorization** will be cancelled and that no bank action or refund is being claimed. A decline or stale preview makes no provider write.

## Durable flow

1. Extend the deterministic customer cancellation action with a distinct policy selection based only on trusted Gateway facts, never a model choice. Preserve the same support-chat link and explicit click-to-review separation.
2. Add a distinct provider facts/guard/marker contract. Include owner/channel, payment identity/state/amount, resolved handler identity/configuration, line quantities, fulfillment/refund counts, and policy version in the digest. The provider performs the final check inside the same local SQLite transaction as the mutation, after acquiring a unique per-order marker lock shared across cancellation policies.
3. Under the transaction context, cancel the exact authorized dummy payment first, verify it is `Cancelled`, then cancel the exact order, verify it is `Cancelled`, inactive, and has zero remaining line quantities, and verify no extra payment/refund/fulfillment appeared. Throw on GraphQL error unions or any mismatch, so a local transaction rolls back payment, order, inventory/history, and marker together. This sequence is **never** generalized to a real PSP, whose external effects are not database-atomic.
4. Gateway reserves a PostgreSQL operation bound to tenant/environment/customer/workflow/preview/payment/facts digest and shares the per-order uniqueness scope with zero-total cancellation. Temporal makes one provider write attempt with no automatic retry. A lost response is pending; subsequent requests and scheduled reconciliation only read the exact marker and fresh order/payment final states. Partial or markerless outcomes remain pending/attention-required, never success.
5. Edge and Customer Portal project only safe preview and status fields. The terminal customer copy names both the order and simulated authorization; a 202 receipt says only that a decision was received.

## Implementation batches

- **Provider and proof first:** add the guarded Vendure plugin API/marker/facts and actual SQLite integration tests. Fault injection after payment cancellation and after order cancellation must prove rollback of payment state, order state/quantities, stock, history, and marker. Test settle/fulfill races and exact replay. Do not enable the customer path until this passes.
- **Gateway and Worker:** add purpose-specific signed assertions, repository/execute/reconcile contracts, Temporal preview/confirmation/state, and tests for ownership, tenant/channel, payment binding, stale consent, changed facts, uncertain outcome, and worker restart. Keep existing zero-total histories compatible.
- **Edge and Portal:** route the existing explicit cancellation CTA to the right policy only after trusted fact evaluation; add safe amount/payment copy, idempotent start, owner-scoped read/confirmation, and regression tests. No automatic mutation from chat.
- **Local integration:** use a fresh disposable, owner-scoped authorized dummy order, run chat → review → exact confirmation → provider final-state verification, and separately test a settled and fulfilled rejection. Browser QA is a separate gate. Never reuse orders already cancelled. Record test identifiers and checks without secrets.

## Acceptance and non-goals

Passing unit/build checks alone is not completion. A clean local end-to-end pass must prove both provider states and marker/ledger agree for the same operation, including uncertain-result recovery. Real PSP voids, settled-order cancellation-plus-refund, exchanges, production identity, and public deployment remain separate work. No automatic destructive cleanup or retention purge is in scope.
